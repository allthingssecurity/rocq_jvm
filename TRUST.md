# Trust base

What a reader has to trust to believe a theorem like `WalCanUpdate.fix_correct`. Everything not on this
list is checked by the Rocq kernel.

## 1. Rocq
- The Rocq 9.3.0 kernel and `rocqchk`. The Rocq standard library (rocq-stdlib 9.2.0) is used only
  through definitions and proved lemmas. The development declares **no `Axiom`s and uses no
  `Admitted`** (this holds for every file in `_RocqProject`, including the Track C files under `theories/Concurrency/`).
  Check: `Print Assumptions WalCanUpdate.fix_correct.` prints "Closed under the global context".
- `vm_compute` (the bytecode VM used for kernel conversion) is used to evaluate the class-file parser
  on the bytes and for the concrete counterexamples. It is part of the standard kernel TCB; for a
  stricter check, replace `vm_compute` by `compute` (slower, same result) or run `rocqchk`.

## 2. The JVM model (theories/Core/*.v)
The semantics is our reading of the JVMS SE 21, chapter 2 and chapter 6. It is the main thing to trust,
and the reason for the differential tests (section 4): every phase compares the extracted model with
HotSpot on random inputs, and a mismatch is treated as a model bug.
- `Int.v`: int/long arithmetic. Corner cases named in the JVMS are checked by `Example`s
  (MIN / -1, MIN % -1, division by zero, shift masks, sign/zero extension).
- `Semantics.v`: one-method small-step interpreter. Instructions without semantics are `Stuck`, and a
  stuck run never yields a result, so an unsupported instruction can make a theorem unprovable but never
  makes a false theorem provable.
- `Float.v`: IEEE 754 arithmetic as functions on bit patterns (one rounding function); correct rounding is
  tested (250,000 inputs per op, 0 mismatches), not proved against real numbers (Flocq is not used).
- `Machine.v`: the multi-frame machine (heap, arrays, exceptions, calls, class initialisation, lambdas).
- `JdkTables.v`: the declared methods and fields (names, descriptors, access flags), superclass and interfaces of
  the JDK classes and interfaces that method/field resolution may reach without loading them; generated by reflection
  on JDK 21 (`tools/gen_jdk_tables.sh`, `tools/GenJdkTables.java`).
- Fast paths of resolution (stated as assumptions, true for any set of classes compiled together by javac): a field
  whose name the object stores once is the field the reference resolves to; a static field key `C.f` that exists is
  the field `C.f` resolves to; the method `resolve_full` finds on the receiver's class is an instance method and the
  referenced method resolves. When resolution would fail for a class changed after its callers were compiled, the
  machine follows full resolution (and throws) only on the slow paths; the differential corpus 7 exercises those.
- Not modelled: threads (Track C), reflection, class loaders, natives without a model. A run that needs any of
  them is `Stuck`, so theorems are only about executions inside the modelled part; the proof itself shows this.

## 3. The loader
- `tools/build-camel-classes.sh`: runs `javac --release 17 -g` (JDK 21.0.12) on the Camel sources
  exported with `git archive` at a recorded commit. Trusted: javac, git. The commit, javac version
  and SHA-256 of each class are written to `classes/<label>/BUILD-INFO`.
- `tools/classdump.py`: copies the bytes of a `.class` file, unchanged, into a Rocq string of hex
  digits (plus SHA-256 and provenance in the header). It does not interpret the file.
  `tools/check-dumps.sh` re-derives the hex and SHA-256 from the class files and compares them.
- `theories/Loader/Hex.v`, `theories/Loader/ClassFile.v`: hex decoding, class-file parsing, constant
  pool resolution and instruction decoding are **inside Rocq**: they are part of the model (section
  2), and are exercised by every differential test, because the extracted harness uses the same
  parser on the same files.

## 4. Differential testing (evidence for 2 and 3, not part of the proof)
- `harness/`: the model is extracted to OCaml (standard extraction of bool/option/list/pair and of
  `string`/`ascii` to OCaml strings/chars; `Z`, `positive`, `nat` stay unary/binary, so no OCaml
  machine arithmetic is involved) and run against HotSpot (`java` 21.0.12, `DiffRunner` via
  reflection) on the same inputs. Counts per method are in `harness/results/*.tsv` and STATUS.md.

- Exception messages of VM-created exceptions are HotSpot 21's texts (the JVMS does not fix them); they are part
  of the model and differentially tested (corpus9 `Msg`, and every uncaught one in the other corpora).

## 5. JDK models (specifications of JDK methods, trusted, differentially tested)
`theories/Jdk/Jdk.v`, `theories/Jdk/Strings.v`. Each modelled method is a Rocq function written from the JDK 21
source of java.base and checked against HotSpot by the corpora `harness/corpus3` (Strs), `corpus2` (Heap),
`corpus5` (Lam):
- `java.lang.String`: length, isEmpty, hashCode, toString, intern, charAt, equals, equalsIgnoreCase (all three
  JDK code paths: Latin-1, mixed, UTF-16 with surrogate pairs), compareTo, indexOf/lastIndexOf (char and String,
  with JDK index clamping), contains, startsWith (both), endsWith, concat, substring (both; identity and `""`
  results as in the JDK), trim, replace(char,char), toCharArray, valueOf(int/long/char/boolean/Object).
- `java.lang.StringBuilder`: constructors, append(String/Object/CharSequence/int/long/char/boolean), toString,
  length, charAt, setLength, deleteCharAt, insert(int,String).
- `java.lang.Character`: toUpperCase/toLowerCase (char and int), isDigit/isLetter/isLetterOrDigit/isWhitespace/
  isUpperCase/isLowerCase, digit, isHigh/LowSurrogate. **Unicode data is a parameter (`uenv`)**: theorems quantify
  over all tables, plus explicitly stated facts checked against JDK 21 by `harness/check_unicode_facts.py`.
- `Integer`/`Long`: parseInt/parseLong (radix 10), toString, compare, Math.max/min/abs, boxing (`valueOf` with the
  JLS caches, xxxValue, equals, hashCode, toString, compareTo), Boolean.TRUE/FALSE.
- `java.util.Objects`: requireNonNull, equals (Strings and boxes), hashCode (Strings).
- `System.arraycopy` (all exception cases, element-wise store check), `Arrays.fill`/`copyOf`, array `clone`.
- `java.lang.Enum`: constructor, ordinal, name/toString, equals. `Object`: constructor, equals, getClass.
- slf4j: `LoggerFactory.getLogger` returns an opaque object; `Logger.isXxxEnabled()` comes from the environment
  (`jenv.j_log_enabled`, theorems state it); every void `Logger` method has no effect on the modelled state.
- Constructors of the java.lang exception classes: no observable state (messages/causes are not modelled);
  `Throwable.getMessage`/`getLocalizedMessage` of a VM-created exception returns its `detailMessage`.
- `Object.notify`/`notifyAll` (one thread: no effect when the caller owns the monitor, else IllegalMonitorStateException);
  `Record.<init>()`.
- `java.lang.Class` (`class_model`): names, simple names, hierarchy queries, isInstance/isAssignableFrom/cast,
  desiredAssertionStatus = false (runs without `-ea`), `Class.forName` for classes the model knows.
- Exceptions created by user code with the java.lang constructors keep their message (`detailMessage`);
  `getMessage` and `Throwable.toString` read it. Causes and stack traces are not modelled.
- `Math` floorDiv/floorMod/addExact/subtractExact/multiplyExact/negateExact/incrementExact/decrementExact/
  absExact/toIntExact; `Integer`/`Long` bitCount, numberOfLeading/TrailingZeros, highest/lowestOneBit,
  rotateLeft/Right, sum, hashCode, signum.
- More `String` methods (`repeat`, `isBlank`, `strip*`, ASCII case conversion, `replace(CharSequence,..)`,
  `split` (one-character fast path), `compareToIgnoreCase`, `join`), `Comparable.compareTo` of Strings and boxes,
  `Integer`/`Long.toHexString`/`toOctalString`/`toBinaryString`, `java.lang.reflect.Array.newInstance`.
- Methods that the JDK defines by other library code run that code's **model class as bytecode** in a frame of its
  own (`Machine.MFrame`): `String.format`/`formatted` (`new java.util.Formatter().format(..).toString()`),
  `String.matches`/`replaceAll`/`replaceFirst`/`split(regex)` (`java.util.regex.Pattern`/`Matcher`),
  `String.valueOf(Object)`, `StringBuilder.append(Object)`, `Object.toString` (virtual `toString`/`hashCode`).
- `classes/jdkmodel` (source `harness/jdkmodel/src`) are **clean-room Java model classes** compiled as a patch of
  java.base: the collections (`ArrayList`, `HashMap`/`LinkedHashMap`/`HashSet`/`LinkedHashSet`, `TreeMap`/`TreeSet`,
  `ArrayDeque`, `Arrays`, `Collections`, `Comparator`, iterators and views, `ConcurrentHashMap`), `Formatter`
  (integer, character, string, boolean and hash conversions with JDK messages for malformed formats; floating
  point and date/time conversions are STUCK) and `java.util.regex` (backtracking matcher; lookbehind, malformed
  patterns and captures the JDK may keep from failed attempts are STUCK). A JDK method missing from a model
  class is STUCK (never `NoSuchMethodError`). Evidence: `harness/targets-{jdkmodel,chm,tree,fmt,sort,deque,regex}.txt`.
Not modelled on purpose: I/O, Method/Field/Constructor reflection beyond the cases above, class loaders.

- Reflection (`reflect_model`, `class_member_model`): the members found, the access rules and the messages follow
  JDK 21 (`Class.getMethod0`, `Reflection.verifyMemberAccess`, `DirectMethodHandleAccessor`); invocation runs
  synthetic bytecode in a frame of its own (`Machine.MFrame`: loads, the invoke, boxing, an exception handler
  that wraps in InvocationTargetException), so the callee is the real bytecode with the machine's dispatch.

## 5a. Virtual machine errors
JVMS 6.3 allows a VirtualMachineError (OutOfMemoryError, StackOverflowError, InternalError) at any point. The
model never throws one: arrays above 2^20 elements are STUCK and there is no stack depth limit. A theorem says
what a run does when no VirtualMachineError occurs, which is all a program can rely on.

## 5b. Threads (`theories/Core/Threads.v`) and the concurrency model classes
- The thread layer is the **sequentially consistent** interleaving semantics: every step of every thread is an
  atomic step of the single-thread machine on the shared heap. For data-race-free programs this is exactly the
  Java memory model (DRF-SC, `Concurrency/DRF.v`, a theorem about the abstract executions; that `tstep` produces
  those executions is not formalised yet). For racy programs the JMM allows more behaviours than `tstep` has, so a
  theorem proved over `tstep` says nothing about the extra (non-SC) behaviours of a racy program.
- JDK model calls (String, StringBuilder, arraycopy, ...) are atomic steps.
- Monitors, wait sets, notify (any waiter: the choice is a parameter of `tstep`), spurious wakeups and timeouts
  (`ts_wakeup`), interrupts and class-initialisation blocking follow JLS 17.1–17.2 and 12.4.2. The run's result is
  the main thread's; daemon status and priorities have no effect.
- **Time.** `System.nanoTime`/`currentTimeMillis` read the run's clock. In the relation `tstep` the clock may advance
  at any step by any amount (`ts_tick`). The executable runs (`trun_gen`) advance it by 1 ns per step; a timed wait
  or sleep ends once the clock has reached its deadline (never earlier: JLS 17.10 for sleep); when no thread can
  step, the clock jumps to the earliest deadline. With `ticks = true` (`call_static_threads_gen`), jumping to the
  earliest deadline is also a scheduler choice at every step, so timeouts can happen while other threads run.
  A theorem over `trun_gen false` covers only the timeout orders that rule produces; over `trun_gen true`, every
  order of the deadlines relative to the threads' steps (time jumps go to deadlines, not to arbitrary instants).
- `classes/threadmodel` (source `harness/threads/src`) are **clean-room Java model classes**, loaded only by the
  machine: `java.lang.Thread` (its private natives are implemented by `Threads.v`; uncaught exceptions go to the
  thread's or the default handler), `ThreadLocal`, the atomics and `LongAdder` (every operation one synchronized
  method: atomic and totally ordered, as the JDK's volatile/CAS operations are under SC; weak CAS never fails
  spuriously), `CountDownLatch`, `Semaphore`, `ReentrantLock` (fair and non-fair) and its `Condition`, blocking
  queues, `ThreadPoolExecutor`, `ScheduledThreadPoolExecutor`, `Executors`, `FutureTask`, `Timer`/`TimerTask`,
  `DelayQueue`. `harness/jdkmodel` adds `ConcurrentHashMap` (bins locked on their first node as in the JDK). They
  are trusted like the java.util model classes and checked the same way (differential tests under six schedulers
  each, `harness/targets-{threads*,chmthreads,sched,pool,time}.txt`).

## 5c. Identity hash codes
- `Object.hashCode`, `Object.toString` and `System.identityHashCode` of an object use `j_ihash` of the
  environment (`jenv`), a function of the heap address, because the JVMS leaves identity hash codes unspecified.
  A theorem fixes it or quantifies over it: a property proved for every `j_ihash` holds on every JVM, a bug shown
  for one `j_ihash` is a behaviour some JVM may have. The differential drivers use a fixed mix of the address, so
  output that depends on identity hash values is not comparable with HotSpot; the java.util models stay STUCK where
  an iteration order would depend on them (HashMap / ConcurrentHashMap tree-bin tie-breaks).

## 5d. Per-run seeds and the default charset
- Values the JDK draws once per run from outside the program are parameters of the environment:
  `jenv.j_seed n` (read by the model classes through the native `java.util.ModelEnv.seed(n)`).
  `j_seed 0` is the SALT32L of `java.util.ImmutableCollections`, which fixes the iteration order of
  `Set.of`/`Map.of` (and of everything built from them, e.g. `Charset.aliases()`) for the run; HotSpot
  takes it from `System.nanoTime()` at startup. As with `j_ihash`, a theorem fixes or quantifies over it.
  The drivers take `MODEL_SEED<n>` from the environment (default a fixed value), so set/map iteration
  orders of immutable collections are not comparable with HotSpot and the tests compare them sorted.
- `Charset.defaultCharset()` is UTF-8 (JDK 18+, unless the JVM runs with `-Dfile.encoding=COMPAT`).

## 5e. Model classes added in the second batch
- `java.util.ImmutableCollections` (List12/ListN/SubList/Set12/SetN/Map1/MapN, KeyValueHolder): JDK 21's
  classes, names, null checks (with HotSpot's helpful NPE messages for the JDK's implicit null checks),
  duplicate errors and the salt-driven iteration of SetN/MapN.
- `java.util.stream` (sequential pipelines with the JDK's push protocol and stream flags), `Collectors`,
  `Optional*`, `StringJoiner`, `java.util.function` (all interfaces and their default methods).
- `java.util.concurrent`: `CopyOnWriteArrayList/Set`, `ConcurrentLinkedQueue/Deque` (removed nodes stay
  in the chain and are skipped: the same traversals as the JDK's lazily unlinked chains),
  `CompletableFuture` (the JDK's dependent stack and claiming, monitors instead of CAS; the default async
  executor is host-dependent in the JDK, so reading its threads' names/daemon status is STUCK),
  `StampedLock` (the JDK's stamp encoding, reader groups and barging).
- `java.nio.charset.Charset`, `StandardCharsets`, `sun.nio.cs.{UTF_8, ISO_8859_1, US_ASCII, UTF_16,
  UTF_16BE, UTF_16LE}` and the String coding of JDK 21 (String.decodeUTF8_UTF16 and the encoders,
  sun.nio.cs.UnicodeDecoder/Encoder with replacement); `java.io.IOException` and four subclasses.
- In `theories/Jdk/Jdk.v`: `Throwable` (cause, initCause, suppressed exceptions, getLocalizedMessage and
  toString dispatched to overrides), `Object.clone` of Cloneable objects (a field copy; otherwise
  CloneNotSupportedException), `java.util.Objects` (callbacks run as bytecode), `System.arraycopy` with
  HotSpot's checks in HotSpot's order and its messages, the String constructors and getBytes, and the
  `Double`/`Float` boxes (no decimal conversion).

## 6. Test drivers and assumptions stated in theorems
- `harness/camel/wal-*/WalScenario.java` and `harness/camel/cim/.../CimScenario.java` are our test drivers for the
  kernel-computed whole-class scenario theorems (`WalScenario.v`, `CimScenario.v`). The unbounded camel-wal theorems
  (`WalRing.v`) use no driver: they quantify over the heap and over every sequence of calls.
- `CimScenario.v` loads two java.util **model classes** of Track B (`AbstractMap`, `Map`; clean-room Java,
  `docs/jdk-collections-status.md`), which are trusted like the Rocq JDK models of section 5 and tested the same way.
  Its case mapping is a concrete table for ASCII and Latin-1 (`l1_uenv`), which agrees with JDK 21 on the characters
  the scenarios use; the 2,000-run differential test of the same driver uses the full JDK 21 tables.
- The camel-wal theorems take the JVM-level preconditions as hypotheses (`wal_env`): the classes are initialised and
  not erroneous, `TransactionLog.LOG` holds a logger, `EntryState.FAILED` a reference; `add` gets a LogEntry object.
  Class initialisation itself is covered by the scenario theorems, not by the unbounded ones.
- The Unicode facts of `CimSpec.jdk_facts` and of `cih_inconsistent_supplementary` are hypotheses of the
  theorems, not axioms; `harness/check_unicode_facts.py` checks them against the JDK 21 tables.
- `CimAscii.ascii_key_laws` instead proves symmetry, transitivity and hash consistency for ASCII keys
  without any Unicode-table hypotheses, for every `jenv`. Its finite character-pair lemma is checked
  by `vm_compute`; induction extends it to strings of arbitrary length. `ascii_bytecode_hash`
  composes this with the existing real-bytecode theorem, retaining the heap and INT_MAX string-length
  preconditions. `CimAsciiMap.ascii_find_correct` instantiates the existing abstract lookup theorem;
  it still requires the table and key representation invariants, and does not cover map resize or sessions.
- `NewBugs.v` uses unchanged Camel `FilterIterator`/`TimeUtils` class files at `bd4d2ba20d6a`.
  Its FilterIterator witness supplies a small ordinary iterator driver (also checked directly as a control);
  HotSpot independently reproduces the defect using JDK ArrayList. Its TimeUtils witness supplies a valid
  normalized Duration heap object and an initialized Duration class, then executes the actual OpenJDK
  21.0.11 Duration getter bytecode. Duration construction/class initialization are outside that witness.
  The existing SLF4J model handles TimeUtils's logger initialization. These are finite counterexamples,
  not universal API proofs; they add no native model or axioms.
